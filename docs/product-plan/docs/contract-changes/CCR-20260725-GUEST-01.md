## Reason (dispute statement)

Two in-flight candidates disagree on the response `data` shape of the prototype endpoint
`POST /api/auth/guest`:

- `codex/prototype-web-demo` @ `d504b4f0c204940edf6cd1f3b8d44f114f32e1bb` assumes
  `{ ok, data: { workspaceId, fixture: { graphId, graphVersionId, strategyVersionId,
  scenarioVersionId, scoreDefinitionId, decisionMakerProfileId, decisionMakerProfileVersion } } }`
  — a nested `fixture` object and **no** `decisionCaseId`.
- `codex/prototype-guest-seed-smoke` @ `3278dd809c1c30103e6949d9aef9f85a49a61b73` actually
  returns flat fields `workspaceId, decisionCaseId, graphId, graphVersionId,
  strategyVersionId, scenarioVersionId, scoreDefinitionId, decisionMakerProfileId,
  decisionMakerProfileVersion, reused` — one extra `decisionCaseId` (plus `reused`), no
  `fixture` nesting.

Left unresolved, the /demo page fails at runtime with its own
`GUEST_PAYLOAD_INVALID` guard the moment both candidates integrate. This CCR issues the single
authoritative shape and one-sided fix instructions. This lane changes no code.

## Evidence (extracted verbatim from the exact SHAs, not from reports)

### E1 — Server (seed) side: flat envelope model

`git show 3278dd80…:services/api/app/auth/guest.py` (lines 64–79):

```python
class GuestBootstrapData(CanonicalModel):
    workspace_id: str
    decision_case_id: str
    graph_id: str
    graph_version_id: str
    strategy_version_id: str
    scenario_version_id: str
```

`CanonicalModel` (`services/api/app/contracts/schemas.py` at base `bd9fde15`) applies
`alias_generator=to_camel` + `serialize_by_alias=True`, so the wire form is camelCase and flat:
`data.workspaceId`, `data.decisionCaseId`, …, `data.reused`. The route answers
`status_code=201` on create and flips to `200` on session reuse
(`response.status_code = 200` in the reuse path of `create_guest`), with
`include_in_schema=False` and the `require_csrf` dependency on the same decorator.

Owner tests already pin the flat shape: `git show 3278dd80…:services/api/tests/test_guest_alpha.py`
defines `ID_FIELDS = ("workspaceId", "decisionCaseId", "graphId", "graphVersionId",
"strategyVersionId", "scenarioVersionId", "scoreDefinitionId", "decisionMakerProfileId")`,
reads them directly from `response.json()["data"]`, and asserts
`data["reused"] is False` (bootstrap, 201) / `second["reused"] is True` (reuse, 200).

### E3 — Canonical envelope discipline

`docs/product-plan/10-api-and-events.md` (base `bd9fde15`): the generic success wrapper is
`{ "ok": true, "data": { … } }` and **every** documented `data` payload in the file is a flat
camelCase object (e.g. intake response `data.decisionCaseId`, run response
`data.simulationRunId`, export response `data.exportArtifactId`). No canonical endpoint nests
identifiers under an intermediate wrapper object such as `fixture`.

`docs/product-plan/docs/contract-changes/CCR-20260724-SIM-02A.md` (frozen, on main):

- Field ruling 1: "**decisionCaseId** — NOT in the request. Derived server-side from
  `graphId → CausalGraph.decision_case_id`."
- Workspace echo ruling: "`workspaceId`, `decisionCaseId`, `graphId` ARE echoed in the
  response … anchors are needed for client-side cache keys and audit display."
- `SimulationRunData` is a frozen flat list beginning
  `simulationRunId, workspaceId, decisionCaseId, graphId, …`.

The Run API implementation (`git show 56e01abd…:services/api/app/simulations/routes.py`,
`_success_payload`) emits exactly `{"ok": True, "data": …}` plus `meta` only on idempotent
replays — the envelope precedent this endpoint must match. The web demo's own
`SimulationRunData` type (E2 file, lines 33–62) already consumes the flat `decisionCaseId`
from run responses, proving the flat convention is what the rest of the demo page uses.

## Adjudication (authoritative shape)

`POST /api/auth/guest` — success envelope, `201` on create / `200` on cookie-bound reuse:

```json
{
  "ok": true,
  "data": {
    "workspaceId": "<uuid>",
    "decisionCaseId": "<uuid>",
    "graphId": "<uuid>",
    "graphVersionId": "<uuid>",
    "strategyVersionId": "<uuid>",
    "scenarioVersionId": "<uuid>",
    "scoreDefinitionId": "<uuid>",
    "decisionMakerProfileId": "<uuid>",
    "decisionMakerProfileVersion": 1,
    "reused": false
  }
}
```

Rulings:

1. **Flat wins; `fixture` nesting is rejected.** The nesting exists nowhere in
   10-api-and-events.md, in any frozen CCR, or in any shipped endpoint; inventing a wrapper
   for one prototype route would fork the envelope discipline for zero benefit. The
   server side is the conforming side.
2. **`decisionCaseId` MUST be exposed.** SIM-02A ruled the run POST body can never carry it
   (`extra=forbid`; server derives it from `graphId`), so the bootstrap response is the only
   pre-run source a client has. Run responses echo it (SIM-02A echo ruling) and the demo's
   own `SimulationRunData` already consumes it; forthcoming case-scoped navigation
   (`/api/workspaces/{id}/…` case surfaces) needs it without forcing a run first. Dropping it
   at bootstrap would be an information regression against an ID the guest already owns.
3. **`reused: boolean` is part of the shape.** It is the body-level discriminator matching
   the 201/200 status split and is already pinned by owner tests (E1). Clients MAY ignore it.
4. **Status codes:** `201` fresh bootstrap, `200` reuse of a valid guest session. Error paths
   stay as implemented: uniform `NOT_FOUND` 404 when `ENABLE_GUEST_ALPHA` is off (route must
   be indistinguishable from nonexistent), `GUEST_BOOTSTRAP_FAILED` 500 `retryable=true` on a
   rolled-back bootstrap, standard CSRF failure envelope otherwise.

## Non-compliant side and one-sided fix instructions

**Non-compliant side: `codex/prototype-web-demo` (frontend).** The server
(`codex/prototype-guest-seed-smoke`) requires **no change**.

Files to change (owner: WEB_DEMO lane or the integration layer; NOT this lane):

1. `apps/web/lib/demo/simulationDemo.ts`
   - Reshape `GuestSession` to the flat payload (add `decisionCaseId: string`; drop the
     `fixture` wrapper from the wire type — the page MAY still regroup fields into an
     internal `DemoFixtureIds` after parsing; the contract binds only the wire shape).
   - `fetchGuestSession`: parse `envelope.data` as the flat object; `validateGuestPayload`:
     require `workspaceId`, `decisionCaseId`, and the seven fixture identifiers as flat
     keys (report missing keys without the `fixture.` prefix); keep the
     `decisionMakerProfileVersion` positive-integer check; tolerate and ignore `reused`.
2. `apps/web/tests/simulation-demo-flow.test.ts` — update guest mocks to the flat payload
   (include `decisionCaseId` and `reused`) and the missing-field assertions to flat key names.
3. `apps/web/tests/simulation-demo-panel.test.tsx` and
   `apps/web/components/demo/SimulationDemoPanel.tsx` — only if they construct or assert the
   nested `GuestSession` shape directly; internal prop shapes are IMPLEMENTATION_FREE.

Acceptance criteria (Vitest, must all pass before the integration layer accepts WEB_DEMO):

- `fetchGuestSession` resolves against a mocked flat payload containing exactly the ten
  `data` keys above and returns `workspaceId` + `decisionCaseId` + the seven identifiers.
- A mocked payload missing `decisionCaseId` (and, separately, each required key) rejects
  with `GUEST_PAYLOAD_INVALID` listing the flat key name.
- A mocked payload with the legacy nested `{ workspaceId, fixture: { … } }` shape rejects
  with `GUEST_PAYLOAD_INVALID` (proves the old assumption is gone).
- No test mocks the nested shape as a success case anywhere in `apps/web/tests/**`.

Server-side acceptance (already green at 3278dd80, re-run unchanged by QA):
`services/api/tests/test_guest_alpha.py` flat `ID_FIELDS` + `reused` assertions.

## Alpha contract status (recorded, not changed)

The route is declared with `include_in_schema=False` and is hard-gated by
`ENABLE_GUEST_ALPHA` (unset/false ⇒ uniform 404, per `guest_alpha_enabled()` and
`_guest_not_found()` in E1; mounted in `services/api/app/main.py` with the same warning).
Consequently:

- `POST /api/auth/guest` is a **prototype/alpha contract**: it does NOT enter the generated
  OpenAPI catalog, `packages/contracts/openapi.json`, or `types.gen.ts`.
- The official `generate_contracts.ps1 -Check` baseline stays `CONTRACT_DRIFT_OK`; this CCR
  introduces no intentional drift.
- Promotion to a public contract requires a future CCR (schema exposure + contracts
  regeneration + 10-api-and-events.md section); until then this document is the only
  authority on the shape.
