# CCR-20260722-004: Subject identity and same-subject aggregate integrity

## Reason

The Task 2 review found two contract-integrity gaps: the persisted `DecisionSubject.slug` was not present in the canonical model/API contract, and Workspace-only foreign keys allowed objects from different Subjects in the same Workspace to be combined. Both gaps can corrupt the Case snapshot, dossier projections, conversation context, and quick-analysis provenance.

## Accepted decisions

### 1. Subject slug

- `DecisionSubject.slug` is a required canonical read field.
- The server generates it during subject creation; clients do not send or update it.
- It is unique within a Workspace and stable/immutable after creation.
- A display-name rename must not silently change the slug.
- `POST /api/workspaces/{workspaceId}/subjects` accepts `name` and optional `description` but not `slug`; subject create/read projections return `slug`.

### 2. Same-subject aggregate references

The following relationships must match Workspace and Subject, not only Workspace:

- `DecisionCase.initiativeId` -> Initiative;
- case-scoped `DossierEntry` -> DecisionCase;
- Case-bound `Conversation` -> DecisionCase;
- `Message` -> Conversation and DecisionCase;
- `QuickAnalysisResult.decisionCaseId` -> the Case bound to its Conversation.

The canonical database implementation uses composite unique keys and foreign keys carrying `workspace_id` and `decision_subject_id`. Domain/API validation must reject invalid combinations before committing a mutation.
