## M7. Mount mechanism: absolute-prefix routers on `app` — VARIANCE (accepted)

**Finding:** the SIM-02A precedent is a **relative** router (`prefix="/simulations/{graphId}"`) included under `workspace_router` (`prefix="/api/workspaces/{workspaceId}"`, router-level `require_workspace_context`). Task 8 and Task 9 instead shipped **absolute-prefix** routers (`APIRouter(prefix="/api/workspaces/{workspaceId}")`) with a per-handler `Depends(require_workspace_context)` on every route — the exact shape their own QA suites mount with `app.include_router(...)`.

**Ruling — VARIANCE, accepted.** Including an absolute-prefix router *under* `workspace_router` would double the prefix; converting the routers to relative would require editing owner code, which the wave boundary forbids ("只挂载不改行为"). Therefore both routers are mounted directly on `app` in `app/main.py`. This is contract-equivalent: the produced paths match the canonical table exactly, and tenancy is enforced per-route by the same `require_workspace_context` dependency (uniform `CASE_NOT_FOUND`/`WORKSPACE_NOT_FOUND` 404). **No owner code touched.** Recommendation (non-blocking, owner follow-up): Task 8/9 owners harmonize to the relative-under-`workspace_router` shape so the guard is enforced by construction; until then the per-route guards are sufficient and tested.

## M8. CSRF posture on `resolutions`/`cancel` — VARIANCE + security follow-up (no code change)

**Finding:** the platform is cookie-based session auth (`_set_session_cookie`). 10-api scopes CSRF to "Cookie mutation" (L5, L946); SIM-02A additionally applied `require_csrf` to its authenticated `POST /runs`. The Task 9 `resolutions`/`cancel` POST handlers carry **no** `require_csrf`.

**Ruling — VARIANCE, mounted as-is.** Under the *literal* canonical scope (CSRF = cookie mutation) these endpoints are compliant, and they were ratified through Task 9 r2/r3 QA + Addendum-A1 without a CSRF finding. A router-level CSRF dependency at include-time cannot be used because it would also (wrongly) guard the SSE `GET`. **Security follow-up (flagged, not fixed here):** given cookie auth, authenticated unsafe writes are CSRF-exposed; the auth/security owner should add `Depends(require_csrf)` to `resolutions`/`cancel` (SIM-02A parity) and the contract should be clarified to state that authenticated unsafe writes under cookie auth carry CSRF. Not fixed this wave (owner code + behavior change).

## M9. Idempotency-Key enforcement on `cancel` — VARIANCE + owner follow-up (no code change)

**Finding:** 10-api L953 lists `cancel` among POSTs that "必须带 `Idempotency-Key`". `post_run_resolution` enforces the header; `post_run_cancel` does not (it relies on natural idempotency — repeated cancel returns the same terminal state; owner tests cover cancel idempotency + terminal guards).

**Ruling — VARIANCE, mounted as-is.** The semantic guarantee L953 protects (no duplicate side-effect on replay) already holds for cancel by construction. **Owner follow-up (flagged, not fixed here):** add `Idempotency-Key` header validation to `post_run_cancel` to satisfy L953 literally. Not fixed this wave (owner code).
