## 2. Profile-aware input hash payload (exact, frozen)

`compute_input_hash` gains one nested top-level object under the canonical key
**`profile`**; every other existing key keeps its exact current shape.

Frozen field contract:

| canonical key | format |
|---|---|
| `profile.id` | canonical lowercase hyphenated UUID string, `str(uuid)` (36 chars) |
| `profile.version` | JSON integer (Python `int`), no string coercion, ≥ 1 |
| `profile.contentHash` | full persisted value `sha256:` + exactly 64 LOWERCASE hex chars; validity regex `^sha256:[0-9a-f]{64}$`; never truncated, never re-cased |

Canonical serialization is UNCHANGED from Task 12: `json.dumps(payload,
sort_keys=True, separators=(",", ":"), ensure_ascii=False)` encoded UTF-8,
digest emitted as `"sha256:" + hexdigest`.

Structure ruling: NESTED object (`"profile": {...}`), not three top-level keys —
it groups one identity, mirrors the existing `strategy` nesting precedent, and
avoids top-level key collisions in future payload evolution.

`riskTolerance` ruling: **kept as the existing separate top-level key with
unchanged semantics.** It is server-resolved from the frozen profile (P1
behavior, already shipped in fb75b8f) but remains an explicit engine input and
an explicit hash field. It is NOT folded into the profile block: the engine
consumes riskTolerance as a numeric input, while the profile block witnesses
identity/content. This preserves Task 12 payload continuity for every
non-profile field.

Identity laws (all MUST hold, and each is independently testable):

1. same (graph, strategy, scenario, scoreDefinition, mode, epsilon, maxSteps,
   nodeOverrides, riskTolerance, profile.id, profile.version,
   profile.contentHash) → same hash, every run, every process;
2. changing ANY ONE of profile.id / profile.version / profile.contentHash /
   riskTolerance changes the hash;
3. same riskTolerance but different profile identity or contentHash → DIFFERENT
   hash (this flips the QA-pinned P2 assertion);
4. preferenceWeights and every other frozen profile field are witnessed through
   `profile.contentHash` (computed by `app/simulations/profile_hash.py` over the
   canonical profile payload — deep key-order independent, QA-proven);
5. the fingerprint passed to the engine MUST come from the VERIFIED frozen
   `decision_maker_profiles` ORM row loaded by the repository
   (`get_decision_maker_profile` under workspace + version + case-scope
   checks). Caller-supplied profile hashes are NEVER accepted anywhere;
6. profile scope/anchor validation MUST complete BEFORE any engine or hash
   computation (already the shipped service order: resolve → validate → engine);
   ghost/foreign/wrong-case/wrong-version references produce the uniform
   404 with ZERO SimulationRun rows persisted.

## 3. Profile content hash trust boundary

**profile_hash_trust_verdict = PERSISTED_HASH_TRUSTED_VIA_APPEND_ONLY_WRITE_PATH
(with mandatory format validation, fail-closed)**

Ruling and evidence:

- The persisted `decision_maker_profiles.content_hash` IS trusted at run time
  WITHOUT per-run recomputation, because three proofs already hold on the exact
  QA combination edaa842: (a) the ONLY write path (repository insert) computes
  the hash itself via `profile_hash.compute_profile_content_hash` and never
  accepts a caller value; (b) profile identity rows are append-only
  (QA-proven double evidence); (c) QA independently recomputed persisted hashes
  and proved byte-equality. Re-hashing every run would add O(payload) cost per
  run for no additional integrity, since there is no mutable path to drift.
- MANDATORY guard: before use in the engine payload, the service MUST
  format-validate the loaded value against `^sha256:[0-9a-f]{64}$`. A missing,
  empty, malformed, or wrongly-cased content_hash is a frozen-reference
  integrity failure: raise the existing stable domain error
  `FrozenReferenceError` (code `frozen_reference_incomplete`) BEFORE any engine
  work; zero SimulationRun rows persisted. It maps to `SIMULATION_INPUT_INVALID`
  422 at the future HTTP boundary per SIM-02A §8 — never a bare
  SQLAlchemy/ValueError.
- Anti-enumeration unchanged: tenant/case/profile ANCHOR failures (ghost,
  foreign workspace, wrong case, wrong version) remain the uniform
  `CASE_NOT_FOUND` 404 path decided before engine/hash computation. The
  format-integrity failure above applies only to a row the caller is entitled
  to reference; it leaks no foreign existence.
- If a future lane adds ANY mutable path to profile rows, this verdict is void
  and a new CCR must re-adjudicate (recompute-and-compare becomes the default).

## 4. Sensitivity and determinism

Frozen rules:

1. The base run and every sensitivity sweep iteration use the SAME frozen
   profile fingerprint (id/version/contentHash) and the same riskTolerance; the
   sensitivity path may not omit, substitute, or re-resolve any of them.
2. The profile fingerprint is iteration-order independent: it is computed once
   from the verified row, never per-iteration, and no dict-iteration order can
   affect it (canonical JSON is sorted at every level).
3. `includeSensitivity` keeps its Task 12 frozen semantics: it is NOT part of
   the inputHash payload (it is absent today and stays absent). No drift
   without an explicit future CCR.
4. This CCR changes ONLY what engine-version/hash identity requires: the
   `ENGINE_VERSION` constant, the `compute_input_hash` payload/signature, and
   the service passing the verified fingerprint. Numeric propagation, damping,
   scoring, convergence, top-driver computation, and recommendation logic are
   UNTOUCHED — Task 12 numeric results must be bit-identical before/after.
5. Determinism law: repeated runs of the same frozen input produce the same
   inputHash AND the same numeric results, across processes.
