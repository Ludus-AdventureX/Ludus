## 2. Profile / riskTolerance authority

**profile_authority_verdict = PROFILE_PERSISTENCE_PREREQUISITE**
**public_post_run_blocked_by_profile = true**

Verified current state on main: there is NO `DecisionMakerProfile` ORM table, no
frozen Charter object readable by ID/version for this purpose;
`SimulationRunService` accepts caller-supplied `decision_maker_profile_id/version`
and `risk_tolerance` and persists them WITHOUT validating that they reference any
real frozen object. Canonical docs (06 §2043-2047, 10 §679) require server-side
validation of frozen Profile references and forbid client-supplied risk preference.

Ruling — before the public POST route ships, a prerequisite slice MUST deliver:

1. An immutable `decision_maker_profiles` persistence object (or equivalent frozen
   Profile snapshot): workspace-scoped, optionally case-scoped, versioned
   (`(workspace_id, profile_id, version)` unique), containing `preference_weights`
   (JSONB), `risk_tolerance` (validated 0..1), and a `content_hash` over the frozen
   payload; rows are append-only (new version = new row, no UPDATE).
2. A tenant-scoped verifiable reference from `simulation_runs` to the profile row
   (composite FK `(workspace_id, decision_maker_profile_id,
   decision_maker_profile_version)` following the SIM-01 frozen-reference FK
   pattern: orphan preflight + `NOT VALID` → `VALIDATE`), via forward migration
   (see §4 — one combined forward revision is acceptable).
3. Service change: `riskTolerance` is RESOLVED SERVER-SIDE from the referenced
   frozen Profile. The API client selects only `decisionMakerProfileId` +
   `decisionMakerProfileVersion`. The service-level `risk_tolerance` request field
   becomes an internal, server-populated value.

Option B was rejected on evidence: no existing table on main holds versioned,
frozen preference/riskTolerance data. Option C is not selected; canonical docs
06/09/10 are NOT amended on this point.

Consequences: the public POST route MUST NOT ship while the service accepts
unverified caller-supplied profile identity or risk tolerance. Internal
service-level callers (tests) are unaffected until the route lands.

## 3. inputHash contract

**input_hash_verdict = ENGINE_HASH_FIX_REQUIRED**
**engine_ccr_required = true**

Verified current state: `engine.compute_input_hash` covers engineVersion, mode,
epsilon, maxSteps, riskTolerance, graph fingerprint, strategy(id/version/
nodeOverrides), scenario fingerprint, score fingerprint, run nodeOverrides. It does
NOT cover `decisionMakerProfileId`, `decisionMakerProfileVersion`, or profile
content (preferenceWeights / content hash). QA has proven two different Profile
ID/versions can currently produce the same inputHash, which contradicts canonical
06 §2047 and 10 §679.

Ruling:

1. Profile identity (`decisionMakerProfileId`, `decisionMakerProfileVersion`) and
   the frozen profile `contentHash` MUST enter `compute_input_hash`.
2. If/where profile `preferenceWeights` participate in scoring, they MUST be part
   of the engine input (via the content hash at minimum); the engine MUST NOT read
   mutable configuration at run time.
3. Changing the hash payload is a replay-contract change and REQUIRES an
   `ENGINE_VERSION` bump (from `sim-engine-1.0.0`) delivered under an INDEPENDENT
   engine CCR (registered here as CCR-ENG-02, owner: Simulation/Graph Owner). This
   also satisfies Addendum A1 ruling 5 discipline (engine semantics change ⇒
   independent engine CCR).
4. Blocking: the public POST route IS BLOCKED until the engine hash fix lands.
   Shipping a public API whose persisted `inputHash` provably violates the
   canonical replay contract would freeze wrong hashes into audit history.
   GET replay is not blocked by this item for rows that already exist, but no
   public rows can exist before POST ships, so both routes effectively ship after
   CCR-ENG-02.
5. Existing persisted test-era hashes are historical; no rehashing/rewrites.

Option B (IDENTITY_EXCLUDED_BY_DESIGN) rejected: it would require amending three
canonical documents to legalize an accident, and replay-exactness across profile
changes would be indefensible.

## 4. Idempotency-Key

**idempotency_verdict = GENERIC_IDEMPOTENCY_RECORDS**
**migration_required = true**

Verified current state: `simulation_runs` has no idempotency column; no generic
idempotency table exists; `inputHash` cannot substitute (the same frozen input may
legitimately be run multiple times on purpose).

Ruling — new generic table `idempotency_records` via FORWARD migration on top of
`a3f8c2d47e19` (which is on main and MUST NOT be rewritten). One combined forward
revision may carry §2 profile tables + this table; a3f8c2d47e19 stays untouched.

Frozen minimum schema:

| column | notes |
|---|---|
| id | UUID PK |
| workspace_id | tenant scope, FK workspaces |
| route_key | stable operation id, e.g. `simulations.runs.create` |
| idempotency_key | raw client header value |
| normalized_request_hash | sha256 over canonical JSON (see below) |
| resource_type / resource_id | e.g. `simulation_run` / run UUID |
| http_status | original terminal status (201 or 409, see §7) |
| response_kind | `success` \| `non_converged` (enum-checked string) |
| created_at | server clock |
| expires_at | created_at + 48h retention; expired rows purgeable |

Frozen semantics (binding regardless of table shape):

1. Unique key scope: `UNIQUE (workspace_id, route_key, idempotency_key)`.
2. Normalized body hash: sha256 over canonical JSON
   (sorted keys, `,`/`:` separators, UTF-8) of the VALIDATED request model
   (post-default-filling) PLUS the path anchors `graphId` (and implicitly
   workspace via key scope). Same key reused on a different graph ⇒ different
   hash ⇒ `IDEMPOTENCY_CONFLICT`.
3. Header format: required on POST; 1..200 chars; visible ASCII (0x21-0x7E);
   missing/oversized/malformed ⇒ 422 `VALIDATION_FAILED` (key not consumed).
4. Atomicity: the `simulation_runs` insert and the `idempotency_records` insert
   commit in the SAME transaction. No run row without its idempotency record on
   this route; no record without its run row.
5. Concurrency: first transaction to commit wins the unique constraint; the loser
   catches the unique violation, re-reads the committed record, and returns the
   replay (same status, `meta.idempotencyReplay = true`). Two concurrent identical
   requests MUST NOT create two SimulationRuns.
6. Failed requests: any failure BEFORE a run row is persisted (validation, 404
   scope denial, capability, CSRF, rate limit, budget, domain 422, GRAPH_NOT_
   CONFIRMED) does NOT consume the key — no record is written. The two persisted
   terminal outcomes (201 success; 409 SIMULATION_NOT_CONVERGED-with-run, §7) DO
   consume the key.
7. Engine-finished-but-response-lost: because run+record commit atomically, a
   retry with the same key+body replays the committed outcome (original status +
   same body + `meta.idempotencyReplay = true`).
8. Same key + different normalized hash ⇒ `IDEMPOTENCY_CONFLICT` 409,
   retryable=false, no details beyond the code (no hash echo).
9. Replay response meta: success envelope gains an optional `meta` object on this
   route; `meta.idempotencyReplay: true` present ONLY on replays.

Option A (columns on simulation_runs) rejected as a dead end for every later
POST surface (from-report, bulk review, branches…). Option C rejected: canonical
10 §950 mandates the header; no doc amendment is made.

## 5. POST request schema (exact, frozen)

Envelope: JSON body, `extra="forbid"`, camelCase. Headers: `Idempotency-Key`
(required, §4), CSRF header (required, §9).

| field | type | req | authority | validation |
|---|---|---|---|---|
| mode | `"experimental"` \| `"formal"` | required | client | enum SimulationMode |
| graphVersionId | UUID | required | client anchor | must belong to path graphId (else uniform 404) |
| strategyVersionId | UUID | required | client anchor | same workspace + same graph (else 404/422 per §8) |
| scenarioVersionId | UUID | required | client anchor | same workspace/case/graph; never bare scenarioId |
| scoreDefinitionId | UUID | required | client anchor | same workspace + graph scope |
| decisionMakerProfileId | UUID | required | client anchor | must reference frozen Profile (§2) |
| decisionMakerProfileVersion | int ≥ 1 | required | client anchor | must match frozen Profile version (§2) |
| epsilon | float | optional, default 0.001 | client | 0 < epsilon ≤ 0.1 |
| maxSteps | int | optional, default 12 | client | 1 ≤ maxSteps ≤ 64 (budget cap, §9) |
| nodeOverrides | object<string, float> | optional, default `{}` | client | see field ruling 7 |

Field-by-field rulings (as tasked):

1. **decisionCaseId** — NOT in the request. Derived server-side from
   `graphId → CausalGraph.decision_case_id`. `extra=forbid` rejects any attempt to
   send it; body can never override the derivation.
2. **graphId** — path `graphId` MUST exactly equal `graphVersion.graph_id`.
   Mismatch is the UNIFORM 404 (`CASE_NOT_FOUND`), not a distinguishable
   `graph_scope_mismatch` — path-level anchors are an anti-enumeration surface.
3. **scoreDefinitionVersion** — SERVER-OWNED. Not accepted in the request
   (single meaning: the service reads the frozen version from the DB and returns
   it in the response). The 10-api example showing it in the request body is
   AMENDED by this CCR (documentation follow-up, P2). No optimistic version match
   on this route: score definitions are frozen rows, not mutable heads.
4. **engineVersion** — SERVER-OWNED. Not accepted in the request; the response
   returns the deployed `ENGINE_VERSION`. Clients cannot select engines. The
   10-api request example is AMENDED accordingly (same P2 doc follow-up). A future
   `expectedEngineVersion` precondition may be added by a later CCR; it is NOT in
   this slice.
5. **riskTolerance** — NOT in the request (consistent with §2): resolved
   server-side from the frozen Profile. The 10-api request example is AMENDED
   accordingly (same P2 doc follow-up).
6. **includeSensitivity** — NOT exposed in the public API this slice.
   Server-fixed `true` (matches the QA-proven service behavior). Not part of the
   idempotency hash (absent from the model), not part of inputHash (already
   excluded by engine contract). Its performance cost is inside the §9 budget.
   Exposure, if ever, requires a later CCR.
7. **nodeOverrides** —
   - merge order: run-level `nodeOverrides` are applied AFTER (override)
     `StrategyVersion.nodeOverrides`, exactly as the engine already consumes them
     as separate inputs;
   - `mode == formal`: run-level `nodeOverrides` MUST be empty `{}`; a non-empty
     map on a formal run fails closed with 422 `SIMULATION_INPUT_INVALID`
     (domainCode `strategy_override_invalid`) — formal replay authority lives in
     frozen StrategyVersions only;
   - keys MUST reference existing graph nodes with controllability
     `decision`/`lever` (existing assembly discipline);
   - included in BOTH the idempotency normalized hash (§4.2) and inputHash
     (already covered by the engine).

## 6. GET replay contract

`GET /api/workspaces/{workspaceId}/simulations/{graphId}/runs/{simulationRunId}`

1. POST and GET return the SAME `data` schema: `SimulationRunData` (below). GET is
   byte-equal replay of the frozen inputs + results.
2. `SimulationRunData` is a NEW wire DTO projected from the service
   `SimulationRunView`. It is NOT the ORM row and NOT the canonical Python
   `SimulationRun` wire schema from CCR-SIM-01 (that schema describes engine wire
   payloads; the API DTO adds anchors/audit fields). ORM rows never cross the HTTP
   boundary.
3. Workspace echo ruling: `workspaceId`, `decisionCaseId`, `graphId` ARE echoed in
   the response (caller already proved workspace membership; anchors are needed
   for client-side cache keys and audit display). No cross-tenant data can appear
   because every query is SQL-bound to the context workspace.

`SimulationRunData` (camelCase, all fields always present unless noted):

```
simulationRunId, workspaceId, decisionCaseId, graphId,
graphVersionId, strategyVersionId, scenarioVersionId,
scoreDefinitionId, scoreDefinitionVersion,
decisionMakerProfileId, decisionMakerProfileVersion,
riskTolerance, engineVersion, scenarioId, simulationMode,
epsilon, maxSteps, steps, inputHash,
nodeResults (object<nodeId, float>),
optionScores (array, canonical order),
topDrivers (array; MAY be empty; shape frozen by service view),
recommendationShift, recommendedOptionId (nullable),
convergenceStatus, originModes (array), createdAt (ISO-8601 UTC)
```

Sensitivity shape: with `includeSensitivity` server-fixed true, `topDrivers` is
always present (possibly empty). No `sensitivity: null` placeholder field exists;
adding richer sensitivity output is a later CCR.

Anti-enumeration (binding):

- repository read MUST bind `workspace_id + graph_id + simulation_run_id` in SQL
  (single SELECT; no fetch-then-check);
- foreign workspace, foreign graph, foreign run, ghost UUIDs, and mixed anchors
  (run exists but under another graph of the same workspace) ALL return the same
  404 signature: `CASE_NOT_FOUND`, one message, no details;
- path graphId vs `row.graph_id` mismatch is exactly this uniform 404.

Implementation requirement (registered): the repository currently has NO
`get simulation run` read method; it must be added in the implementation slice
(read-only, workspace-scope-bound, returning the service view).

## 7. HTTP status + non-convergence

- POST, new run, converged (or experimental any-convergence): **201 Created**.
- Idempotent replay: original terminal status replayed (201 or 409), body
  identical, `meta.idempotencyReplay = true`.
- GET: **200 OK**.

**Formal non-convergence verdict = B (persist + 409 SIMULATION_NOT_CONVERGED):**

- The run IS persisted (auditable, satisfies 10 §681 "非 converged formal 结果保持
  可审计") in the same transaction as its idempotency record;
- the HTTP response is **409 `SIMULATION_NOT_CONVERGED`**, retryable=false,
  `details.simulationRunId = <persisted run id>` and
  `details.convergenceStatus = <value>` (safe, tenant-scoped);
- replays with the same key+body return the SAME 409 with the same details;
- downstream consumer gate (binding on SIM-05/06 and Decision lanes): a formal
  run with `convergenceStatus != converged` MUST NOT feed PDF export, formal
  recommendation, or DecisionRecord; gates re-check convergenceStatus at
  consumption time and fail with `SIMULATION_NOT_CONVERGED`.

Option A rejected: a 2xx would make client-side misuse of non-converged formal
runs the default failure mode. Option C rejected: violates auditability (§681).

**Experimental non-convergence:** 201 Created; `convergenceStatus` reports the
truth; no error. Experimental runs are barred from formal surfaces regardless of
convergence (existing canonical rule).

## 8. Error mapping (exact, frozen)

Mapping is BY EXCEPTION TYPE / stable `code` attribute only. String matching on
exception messages is FORBIDDEN (closes prior P3 on
`SimulationAuthorizationError`).

| domain source (code) | API error code | HTTP | retryable | safe details |
|---|---|---|---|---|
| repo scope denial (`simulation_scope_not_found`) — missing/foreign/mixed anchors, incl. path graphId mismatch, unverifiable Profile ref (§2) | `CASE_NOT_FOUND` | 404 | no | none |
| `FrozenReferenceError` (`frozen_reference_incomplete`) | `SIMULATION_INPUT_INVALID` | 422 | no | `{ "domainCode": "frozen_reference_incomplete" }` |
| `GraphScopeMismatchError` (`graph_scope_mismatch`) — same-workspace cross-graph anchors | `CASE_NOT_FOUND` | 404 | no | none (anti-enumeration precedence; see note) |
| `StrategyOverrideError` (`strategy_override_invalid`) | `SIMULATION_INPUT_INVALID` | 422 | no | `{ "domainCode": "strategy_override_invalid" }` |
| `ScenarioParameterError` (`scenario_parameter_invalid`) | `SIMULATION_INPUT_INVALID` | 422 | no | `{ "domainCode": "scenario_parameter_invalid" }` |
| `ScoreDefinitionReferenceError` (`score_definition_reference_invalid`) | `SIMULATION_INPUT_INVALID` | 422 | no | `{ "domainCode": "score_definition_reference_invalid" }` |
| assembly fail-closed (`strategy_edge_gating_unsupported`) | `strategy_edge_gating_unsupported` | 422 | no | none |
| assembly/engine fail-closed (`score_constraint_operator_unsupported`) | `score_constraint_operator_unsupported` | 422 | no | none |
| `SimulationAuthorizationError` / `FormalAuthorizationError` (`formal_authorization_rejected`) | `GRAPH_NOT_CONFIRMED` | 409 | no | none |
| formal non-converged result (§7) | `SIMULATION_NOT_CONVERGED` | 409 | no | `{ "simulationRunId", "convergenceStatus" }` |
| idempotency same-key/different-hash | `IDEMPOTENCY_CONFLICT` | 409 | no | none |
| `SimulationPersistenceError` (`simulation_persistence_failed`) | `SIMULATION_PERSISTENCE_FAILED` | 500 | yes | none — NEVER SQLAlchemy/asyncpg internals |
| missing capability | `MEMBERSHIP_CAPABILITY_REQUIRED` | 403 | no | `{ "requiredCapability" }` (existing shape) |
| CSRF failure | `CSRF_VALIDATION_FAILED` | 403 | no | none |
| rate limited | `REQUEST_RATE_LIMITED` | 429 | yes | `{ "retryAfterSeconds" }` |
| budget exceeded (§9) | `SIMULATION_BUDGET_EXCEEDED` | 422 | no | `{ "budget": "<dimension>" }` only |
| body/header validation | `VALIDATION_FAILED` | 422 | no | sanitized errors (existing envelope) |

Binding notes:

1. **Addendum A1 rule preserved literally**: the two stable codes
   `strategy_edge_gating_unsupported` and `score_constraint_operator_unsupported`
   appear VERBATIM as the envelope `error.code` (lower-snake), a deliberate,
   documented exception to the uppercase API-code convention. They remain 422 and
   MUST survive every later SIM CCR unchanged.
2. `GRAPH_VERSION_NOT_FOUND` (10 §930) is NOT used by these two routes: on the run
   surface every existence denial collapses into the uniform `CASE_NOT_FOUND` per
   the shipped anti-enumeration QA. `GRAPH_VERSION_NOT_FOUND` remains reserved for
   SIM-02B graph-read routes. `SCENARIO_VERSION_MISMATCH` (10 §932) likewise stays
   reserved for working-copy/preview surfaces (SIM-04); on this route
   cross-anchor denials are 404/422 as mapped above. Registered as P2 doc
   clarification, not a code retirement.
3. New API codes introduced by this CCR (to be added to the 10-api error table in
   the P2 doc follow-up): `SIMULATION_INPUT_INVALID` (422),
   `SIMULATION_PERSISTENCE_FAILED` (500), `SIMULATION_BUDGET_EXCEEDED` (422), plus
   the two verbatim lower-snake codes above.

## 9. Capability / CSRF / rate limits

**capability_matrix (frozen):**

| operation | requirement |
|---|---|
| POST run, `mode=experimental` | active membership + `contribute` |
| POST run, `mode=formal` | active membership + `contribute` (formal authority is enforced by graph state `GRAPH_NOT_CONFIRMED` + downstream review/sign gates, which stay untouched) |
| GET run | active membership only (read parity with the lens consumption read-path precedent) |

Membership-only users can NEVER execute a simulation (POST requires
`contribute`); reading persisted results is workspace-membership read parity.

Binding rules:

- both routes resolve tenancy EXCLUSIVELY through `require_workspace_context`
  (mounted on `workspace_router`); the simulations router performs NO membership
  parsing of its own;
- POST passes through the existing `require_csrf` dependency (cookie-auth
  mutation); GET requires no CSRF;
- no route accepts caller-supplied user identity or workspace authority in body
  or headers; the principal comes from the session only;
- rate limiting REQUIRED on POST: per (workspace, user) sliding window following
  the existing fail-closed limiter pattern; defaults frozen at 10 POST runs /
  5 minutes per user per workspace (tunable via settings, floor documented);
  over-limit ⇒ `REQUEST_RATE_LIMITED` 429 + `retryAfterSeconds`;
- synchronous execution budget (fail-closed BEFORE engine start):
  `maxSteps ≤ 64` (schema), graph size guard ≤ 500 nodes / 2000 edges per
  graphVersion (checked after load), sensitivity included in budget;
  over-budget ⇒ `SIMULATION_BUDGET_EXCEEDED` 422;
- rate limiting and idempotency are INDEPENDENT mechanisms: a 429 never consumes
  an Idempotency-Key; an idempotent replay is exempt from the run budget (it
  executes no engine work) but still passes the rate limiter.
