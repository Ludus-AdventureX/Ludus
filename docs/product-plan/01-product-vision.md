# 01. 产品愿景

## 定位

**Ludus — 预见未来，保障您的事业。**

Ludus 是面向实际决策人的企业战略决策沙盒，帮助创始人或产品方向负责人把模糊问题变成可审计的决策档案。“预见未来”表示提前看见假设、因果路径、风险和建议翻转条件，不表示精确预测一个未来结果。系统核心不是给出一个看似确定的答案，而是让决策人明确：已知什么、未知什么、相信什么、偏好什么、正在承担什么风险，以及在什么条件下应该改变决定。P0 支持 Workspace 隔离，但不以团队审批、投票或实时共创为主流程。

## 最先服务的细分场景

首个 P0 场景：硬科技初创团队中的实际决策人判断球形机器人应优先进入救援市场还是家庭服务市场。

选择该场景的原因：

- 决策通常发生在信息不足但时间紧迫的阶段，AI 能明显降低资料整理和假设检查成本。
- 决策涉及市场、客户、产品、竞争、渠道、财务和团队能力，适合用结构化 `DecisionCase` 串联讨论、报告和沙盘。
- 结果天然需要行动项、领先指标和复盘日期，适合展示闭环。
- P0 使用真实但不敏感的球形机器人市场方向案例：资金与研发资源有限时，优先进入救援市场还是家庭服务市场。

## 目标用户

| 用户 | 典型职责 | 关键诉求 |
|---|---|---|
| 创始人/CEO | 判断方向、资源投入、融资叙事 | 快速看清关键假设和下注条件 |
| 产品负责人 | 定义产品方向、验证需求、排优先级 | 把用户证据、机会和风险连接起来 |
| 战略/增长负责人 | 评估市场进入、渠道、竞争动作 | 需要可引用、可复盘的决策依据 |
| 投资或创新团队 | 审查项目、提出反方意见 | 需要标准化尽调和情景推演 |

P0 优先照顾前两类用户：创始人和产品负责人。他们对工具复杂度容忍度低，但对高质量澄清问题、证据链和可行动建议有强需求。

## 用户现在如何决策

当前常见流程：

1. 在会议、聊天软件和临时文档中提出问题。
2. 让团队成员各自搜集资料，来源和口径不统一。
3. 用一个会议或文档汇总结论，但事实、假设和偏好混在一起。
4. 最终决定由负责人拍板，后续行动、指标和复盘时间不完整。
5. 几周后环境变化，团队很难知道当初的判断依据是否仍成立。

痛点集中在五类：

- 证据分散：链接、截图、主观经验和模型回答混杂，难以追溯。
- 假设隐形：真正决定成败的假设没有被明确记录。
- 反方不足：团队容易围绕主流叙事形成一致幻觉。
- 输出断裂：聊天、报告和后续跟踪不是同一个对象。
- 无法复盘：没有记录当时条件、阈值、退出条件和领先指标。

## 价值主张

Ludus 为每个决策提供七个结果：

- 一个版本化 `DecisionCase`，记录本次决策的 5W1H、目标、选项、Case-local 条目和档案快照引用；主体长期事实、约束和偏好由 `DecisionSubjectDossier` 管理。
- 一个证据账本，标注来源等级、时间、相关性、冲突状态和适用范围。
- 一个论证树，展示选项、支持理由、反对理由、关键假设和证据连接。
- 一个深度决策报告，包含一页简报、详细分析、引用和反方审查。
- 一个可编辑因果沙盘，用于查看关键变量变化对建议的影响。
- 一个可版本化实验空间，支持创建分支、比较方案和从历史版本非破坏性回滚。
- 一个由授权人类签署、不可变且可追加修订的决策记录，保存最终决定、条件、阈值、退出条件、领先指标、来源 Run/Report 和复盘日期。

## 可信度机制

Ludus 的可信度来自过程约束，而不是宣称模型更聪明：

- 结构化分类：每个关键条目必须标注为事实、证据、假设、判断、偏好或未知项。
- 来源等级：参考 `探讨/skills/research/v6-rag-pool/SKILL.md` 的来源分级思路，P0 至少区分官方/一手资料、可信媒体或研究、普通网页、不可验证来源。
- 冲突处理：同一命题出现相反证据时，标记为 `conflicted`，要求综合阶段说明影响。
- 反方审查：参考 `探讨/skills/research/v6-devils-advocate/SKILL.md` 的核心假设压力测试和致命缺陷检查。
- 安全锚点：参考 `探讨/skills/research/v6-safety-anchor/SKILL.md`，系统持续追问集体盲点和主流叙事回声。
- 人工确认：正式档案变更、Analysis Charter、正式因果节点/边采纳和最终决定保存前要求用户确认；质量门通过的报告不再增加第二次发布确认。

可信度边界：

- 系统追溯用户可见的命题、证据、假设、方法版本、工具调用摘要、状态变化、因果边和建议，不展示模型内部思维链。
- 系统降低无依据内容进入正式输出的风险，不承诺消除大模型幻觉。
- 系统分别表达证据可用性、命题支撑、假设稳定性、因果可信度、战略稳健性和流程质量，不把综合指标解释为正确概率或成功概率。

## 为什么不是普通聊天机器人

普通聊天机器人通常以对话轮次为中心，历史上下文难以稳定沉淀，输出也很难被复用。Ludus 以主体档案和 `DecisionCase` 为中心，对话先生成候选变更，用户确认后才更新正式数据。

关键区别：

- 聊天机器人返回答案，Ludus 更新可版本化档案。
- 报告生成器产出文档，Ludus 让报告、证据、假设和沙盘互相引用。
- 普通 AI 难以说明建议边界，Ludus 要求建议带条件、阈值和退出信号。
- 普通工具很少复盘，Ludus 把最终决定、行动项、领先指标和复盘日期作为一等对象。

## 工程可信交付指标

除产品行为指标外，Alpha 还必须满足：OpenAPI/TypeScript 合同生成无漂移；跨 Workspace、CSRF、SSRF、密钥脱敏和 fixture 来源测试通过；每个多智能体 Task 有唯一 write owner、完成证据和 handoff。工程指标不替代报告质量，但任何失败都阻止对外 Demo 发布。

## 成功指标

P0 演示成功指标：

| 维度 | 指标 | P0 目标 |
|---|---|---|
| 完整性 | 端到端链路完成率 | 预置案例 100% 完成 |
| 澄清质量 | AI 提出高价值澄清问题 | 至少 6 个问题，覆盖目标、约束、证据、假设、风险 |
| 可追溯性 | 关键结论可回到证据 | 正式报告的核心判断至少关联 1 条通过质检的证据；非核心判断若仅为假设必须显式标注 |
| 支持准确性 | 引用内容真实支持关联命题 | 预置核心命题人工核验 100%，反对证据与支持证据不混用 |
| 可质疑性 | 反方审查产出 | 至少 3 条反对理由和 2 个脆弱假设 |
| 沙盘可用性 | 因果图可编辑并重新计算 | 至少 8 个节点、10 条边、三情景切换和敏感性排序 |
| 推演可复现 | 相同版本输入得到相同结果 | 推荐翻转条件由验证脚本稳定复现，分支比较和回滚不覆盖历史 |
| 降级诚实性 | 外部服务状态可辨认 | `live`、`cached`、`fixture` 全链路可见，fixture 不冒充实时结果 |
| 决策闭环 | 最终记录完整 | 决定、条件、行动项、领先指标、复盘日期均可保存 |

## 产品原则

- 先让一个高风险决策跑通，再扩展到更多决策类型。
- 先建立可审计数据结构，再追求更复杂的 Agent 编排。
- 先表达不确定性，再给建议。
- 先支持人工修正，再谈自动化。
- 不要求用户先选模板；从对话理解问题，在正式分析前冻结方法和范围。
- 第一版沙盘只做因果推演和敏感性分析，不承诺精确预测未来。
