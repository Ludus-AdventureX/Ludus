## 一句话定义

**Ludus — 预见未来，保障您的事业。** Ludus 是面向实际决策人的企业战略决策沙盒。它以决策主体为长期记忆中心，以版本化 `DecisionCase` 为正式工作单元，以可插拔方法论包为分析能力，通过日常问答、深度分析和沙盘模拟，把模糊问题转成可追溯、可质疑、可干预、可回滚、可复盘的决定。“预见未来”指提前识别假设、影响路径和翻转条件，不指精确预测。

系统不替用户决定，不展示不可验证的模型内部思维链，不把沙盘包装成精确预测。用户控制分析什么、允许使用哪些正式事实以及最终采纳什么；系统负责方法编排、信息质检、对抗检查、因果推演和过程审计。

可追溯范围限定为用户可见产物：命题、证据、假设、判断、方法版本、工具调用摘要、状态变化、因果边、模拟输入和建议。系统不保存或展示隐藏思维链来证明可信度。

## 首个用户与首个场景

首个用户是硬科技初创团队中的实际决策人，通常是创始人或对产品方向承担最终责任的人。P0 不以团队共创、审批或投票为主流程。

首个场景是高切换成本的产品与市场方向选择：

> 资金与研发资源有限的球形机器人项目，应该优先进入救援市场，还是家庭服务市场？

该场景同时暴露技术成熟度、产品改造、客户需求、采购周期、现金消耗、安全责任、竞争替代和路线切换成本，适合验证完整决策闭环。

## 产品权力边界

### 决策人的权力

- 决定某个问题是否值得分析。
- 选择快速框架分析、聚焦研究或完整战略分析。
- 确认进入正式档案的事实、约束、偏好和判断。
- 修改分析方向，但不能要求系统伪造已通过质量门的状态。
- 在沙盘中创建任意实验分支。
- 决定哪些分析结论写回档案。
- 保存、调整、撤销或结束最终决定。
- 决定是否向社区贡献脱敏方法论经验，以及是否另行授权模型训练。

### 系统的权力

- 根据问题复杂度、信息缺口和成本推荐分析等级，但不判断决策价值。
- 将不合格来源隔离为 `lead_only` 或 `rejected`，不得作为核心结论的正式依据；允许 Critic 查看被拒材料以解释其为何不可用。
- 阻断不合格结论进入正式报告。
- 阻断无依据或低质量的关键因果边进入正式沙盘。
- 在核心事实冲突、问题失效、致命缺陷或关键输入缺失时中断深度分析并请求用户介入。
- 对未通过质量门的分析只交付草稿、缺口和验证建议，不冒充正式结论。

## 多租户与记忆主体

`Workspace` 是安全和数据所有权边界，`DecisionSubject` 是长期记忆边界，`DecisionCase` 是一次正式决策的聚合根和版本边界。三者不能合并。

```text
User
└── WorkspaceMembership
    └── Workspace
        └── DecisionSubject
            ├── DecisionSubjectDossier
            └── Initiative
                └── DecisionCase
                    ├── MethodRecommendation
                    ├── AnalysisCharter
                    ├── AnalysisRun
                    ├── ReportArtifact
                    ├── CausalGraph
                    ├── DecisionRecord
                    └── Review
```

一个用户可以加入多个 Workspace。P0 只需要 `owner` 和 `member` 两个角色，产品交互仍以单一决策人使用为主，不做实时协作和复杂权限矩阵。

系统分别维护：

- `DecisionMakerProfile`：风险偏好、价值排序、经验、已确认偏差和决策习惯。
- `DecisionSubjectDossier`：企业、项目或产品的资源、约束、技术、客户、证据、假设和历史决定。

个人偏好不能被当成项目事实，某个项目的结论不能污染其他主体。长期事实、约束和偏好保存在 `DecisionSubjectDossier`；`DecisionCase` 保存本次决策问题、目标、选项和 Case-local 条目，并冻结本次选用的长期档案条目。分析结果只生成候选更新，由用户决定写回 Case 还是主体长期档案。

Case 生命周期只表达决策本身：`draft → scoped → ready → running → review → pending_signoff → decided → monitoring`。`blocked/needs_attention/cancelled/reopened/archived` 只作为 operational status 或 Run 状态。系统只能依据真实 Run 事件推进到 review，且永远不能自动从 pending_signoff 进入 decided；同一 Case 可保留多次历史 `AnalysisRun`，P0 同时最多允许一个活动正式 Run。

## 双层决策档案

用户看到的是一份可阅读、可编辑、可随时调出的动态“决策档案”；系统底层保存结构化条目、来源、状态、作用域和版本。

档案条目类型：

- `fact`：经用户确认或有合格来源支持的事实。
- `evidence`：支持或反对某命题的外部或内部材料。
- `assumption`：决策依赖但尚未验证的前提。
- `judgment`：用户或系统基于材料形成的判断。
- `preference`：决策人的价值偏好和风险权重。
- `unknown`：影响决策但当前缺失的信息。
- `constraint`：资源、时间、法律、技术或组织硬约束。

档案条目状态：

- `candidate`：从日常对话中提取，尚未确认。
- `confirmed`：用户确认，可进入正式档案和分析快照。
- `rejected`：用户否决，保留事件记录但不参与分析。
- `expired`：曾经有效但已过期。
- `conflicted`：存在相反材料，必须在分析中显式处理。

档案不直接覆盖旧值。确认、修订、否决和过期都生成事件与新版本。深度分析读取冻结快照；沙盘读取分析版本并创建实验分支。

## 三种产品模式

### 日常问答

日常问答是登录后的默认入口，也是长期理解决策人和项目的主要方式。它负责自由讨论、接收材料、提取候选记忆、补充信息、调用已授权数据源，以及将一个问题整理为正式分析任务。

日常问答不能静默修改正式档案。系统在后台生成候选变更，用户可以确认、修改、否决或暂不处理。高影响内容必须显式确认，包括核心技术路线、目标市场、资金约束、长期风险偏好和项目停止/继续状态。

系统可以识别“可能的决策问题”，但不能判断其是否值得分析。用户可继续讨论、启动快速框架分析，或准备深度分析。

用户不需要先选择决策模板。系统从对话和已确认档案中识别决策类型、目标、约束、选项和未知项；用户只决定是否分析，并选择快速分析、聚焦研究或完整战略分析。快速分析直接生成会话内 `QuickAnalysisResult`；聚焦/完整分析的方法包由系统推荐，并在 Analysis Charter 中显示名称、版本、理由和边界。

### 深度分析

进入深度分析前，系统先运行版本化 `MethodRouter`，再生成一页 `AnalysisCharter`，包括：

- 决策问题与决策期限。
- 决策主体与档案快照版本。
- 成功标准和硬约束。
- 当前选项、当前倾向和可能偏见。
- 已确认材料、关键未知项和不允许进入分析的内容。
- 建议分析方向、方法论理由、替代方法和适用边界。
- 用户选择的分析等级、方法包 ID/版本/哈希、匹配状态、缺失输入和是否允许正式分析。

用户确认业务问题、方向、事实范围和约束。系统自动编排方法，不要求用户成为方法论专家；主界面不使用模板卡片墙。Charter 确认后冻结档案快照、范围、分析等级、方法版本、允许材料和预算，修改必须创建替代 draft。旧 confirmed Charter 在替代 draft 尚未确认时继续有效；新 Charter 确认后旧 Charter 才标记为 `superseded`。分析中默认不打断用户，仅在重大异常时请求介入。质量门通过即生成 ready 报告，不增加发布前二次确认；最终报告只产生候选档案更新，用户验收后才写回。

深度分析包含两个等级：

1. **聚焦研究**：1-2 个方向，定向检索，研究/批判/综合/校验，交付执行简报和证据账本。
2. **完整战略分析**：3-4 个方向，证据池、多 Agent 迭代、交叉阅读、研究、批判、综合、校验、完整质量门和正式沙盘。Safety Anchor 与魔鬼审查属于 Critic 的强制子阶段，参谋长建议结构由 Synthesis 产出，正式 Worker 始终只有四类。

full 还强制生成五个独立、Workspace-scoped `StrategicLensArtifact`，不是在报告中增加五个装饰标题：Research 产出 `porter_five_forces`；Critic 产出 `pre_mortem` 与 `counterparty_response_matrix`；Synthesis 产出 `scenario_planning` 与 `meadows_leverage_points`；Validation 验证但不得补写。`StructuredReport.lensArtifactIds` 只引用这些不可变 artifact，用户可从报告逐个读取其证据、假设、行为结构和来源 Run。

报告页先读取轻量 `StrategicLensArtifactSummary[]` 来展示五项导航、producer/status、引用计数、版本/hash/origin 和完成时间；summary 不含 `content` 或 `researchRequests`。用户打开单项时才读取完整 `StrategicLensArtifact` 判别联合，因此列表扫描不会重复传输五份 lens 内容，且 item 仍保留完整审计细节。

五项 lens 必须复现已发布方法包的严格行为：Porter 对每个市场完整五力、证据/趋势/监管和非公式化战略含义；Pre-Mortem 三视角、至少 5 cause、top 3 prevention/contingency/detection 与明确 verdict；Counterparty 以 1-2 个关键 actor、含 no-action 的可观察行动、一层 optimal/worst/likely response、publication test、下行不对称和反身性为边界；Scenario 分离预决因素与不确定性，以两个 axis 形成至少三个结构不同情景、timeline/stakeholder/early warning 和逐策略韧性测试，至少一个策略在一个情景中被 killed；Meadows 映射 stocks/flows、反馈、延迟、规则/激励，覆盖至少三个层级并暴露被忽略的高杠杆、失控强化回路和副作用。

用户仍只选择 `quick/focused/full`，不逐项选择 lens。focused 不创建这些 artifact；full Charter 的 `requiredStrategicLensTypes` 固定为五项完整集合，并随快照、方法和预算一起冻结。运行中增删 lens 是 amendment，必须 replacement Charter + new Run，不能修改 confirmed Charter、恢复旧 Run 或覆盖历史 artifact。

快速框架分析保留在日常问答中，只使用已确认档案和轻量方法，保存为 `QuickAnalysisResult`，不创建 Charter、正式 `AnalysisRun`、正式报告、PDF 或沙盘。

### 沙盘模拟

沙盘是可干预的因果决策模型，不是预测器。它回答：决定会影响什么、为什么产生该结果、哪些因素可控、哪些不可控、在不同外部环境下哪种战略更稳健。

沙盘默认面向“需要判断当前建议是否经得起变化”的决策人，而不是面向因果建模专家。用户进入沙盘后的首要任务不是编辑完整图，而是完成一次有明确起点和结果的压力测试：查看当前建议及其最脆弱条件，选择一个需要验证的条件，调整变量或切换情景，理解关键影响路径与翻转阈值，再决定保存实验、生成验证行动或采纳候选更新。完整因果图、逐节点/边审阅、分支比较和回滚作为渐进展开能力保留。

节点类型：

- `decision`：决定或战略动作。
- `lever`：决策人可控制的杠杆。
- `constraint`：当前不可突破的硬约束。
- `external`：不可控制但可设置情景的外部因素。
- `unknown`：当前未知、可补充或可验证的因素。
- `intermediate`：中间结果。
- `outcome`：最终结果。
- `indicator`：领先指标。

每条边包含方向、强度、时间延迟、关系存在可信度、来源和确认状态。关系存在可信度与影响强度必须分开表达。

战略是决策人主动采取的一组行动；情景是外部因素和未知项的一组假设；模拟是在某个情景中运行某个战略。正式沙盘应比较结构不同的情景，乐观/基准/悲观只作为快速预设。

沙盘输出包括一至三阶影响、关键可控杠杆、外部监测变量、脆弱因果边、推荐翻转条件、敏感因素、硬约束触发和最值得验证的未知项。修改默认保存在实验分支，只有用户采纳后才生成候选档案更新。

P0 默认交互顺序固定为：

1. 显示当前条件化建议、适用条件和“不代表精确预测”提示。
2. 从敏感性结果和低关系质量路径中展示最多三个最脆弱条件，并说明它们为什么重要、是否可控以及当前证据状态。
3. 用户选择一个条件进行压力测试；系统优先提供业务单位滑杆或已确认情景，不要求用户理解图模型字段。
4. 运行后同时显示相对基线变化、建议是否保持、翻转阈值、触发的硬约束和一至三阶关键影响路径。
5. 用户可将结果转为验证行动、保存为命名实验分支，或进入“展开完整模型”审阅和编辑节点/边。
6. “采纳到决策”只创建候选更新；最终决定仍由用户在决定保存流程中确认。

P0 的最小版本能力是：编辑进入工作副本并支持 undo/redo；保存生成不可变 graph version；用户可从任意历史版本创建命名分支、比较两个版本，并通过从历史版本创建新当前版本完成非破坏性回滚。每次运行固定引用 graph、strategy、scenario、score definition 和 engine 版本。

`scenario_planning` artifact 是战略情景分析，沙盘 `ScenarioVersion` 是用户审阅接受某个 frame 后生成的独立投影，两者不得混用。ScenarioVersion 保存来源 lens/frame、策略是否存活和 early warning，只表达 external/unknown；决策人风险偏好留在冻结 Charter/ScoreDefinition/Strategy，不进入 ScenarioVersion。

### 自定义影响因素

完整模型允许用户自行添加影响因素，但该能力服务于人的思考，而不是把沙盘变成自动建模器：

- 默认压力测试不展示新增控件；用户主动展开完整模型后才出现“添加影响因素”。
- 用户可以自然语言描述因素，系统只生成候选定义与候选关系。
- 因素的业务含义、范围、可控性、证据状态和关系必须由用户确认、修改或否决。
- 无证据因素作为 `assumed/unknown` 进入实验工作副本，不能冒充观察事实。
- 工作副本修改可以及时生成可解释的实验预览，但预览不进入正式报告、决定或推荐。
- 正式结果必须经过不可变 GraphVersion、确认门与主动运行。

这使沙盘既允许开放建模，又保留版本纪律、证据责任和“人是最终解释者”的产品边界。
## 数据连接器与 MCP 演进

MCP/插件属于证据获取层，不属于可信度判断层。方法论包决定需要什么信息，连接器负责获取，信息质检层决定是否可用。

```text
Unknown / RetrievalTask
→ Connector Registry
→ MCP / Web / File / Internal API
→ Immutable Raw Artifact
→ Evidence Normalization
→ Information Quality Gate
→ Evidence Ledger
→ Claim / Factor / CausalEdge
```

P0 通过直接 HTTP API Provider Adapter 内置 Exa 搜索、Firecrawl 抓取和 Tavily 备用，并允许用户从审核目录添加自己的 API Key。Agent 只看到稳定、只读、MCP-compatible 的能力接口。实现参考 Hermes `mcp_tool.py` 的 schema 转换、命名空间、超时、错误清洗和连接生命周期，但 72 小时内不开放任意 MCP URL、stdio/npx、自定义 OAuth、写操作和高敏权限。每次调用携带 Workspace、权限范围、查询参数、时间、额度、原始结果哈希、`originMode` 和审计事件。

外部证据可以不经逐条用户确认参与本次分析，但必须通过信息质检；由证据推导的新结论、档案变化，以及自动生成的因果节点和边必须在最终验收时 bulk review 并确认、修改或否决。

## 信息质检与分析质量门

系统设置两个独立质量层。

### 信息质量层

数据进入分析前检查真实性、来源等级、相关性、时效性、适用范围、独立性、偏见方向、完整性、冲突状态和提取可靠性。

证据结果：

- `accepted`：可支撑主要判断。
- `conditional`：可以使用，但必须携带适用条件和警告。
- `lead_only`：只作为检索线索，不能支撑主要结论。
- `rejected`：不允许进入推理。

多个网页引用同一份原始报告只能算一个独立来源。来源权威度、来源偏见和证据相关性是不同维度，不能相互替代。

### 分析质量层

分析完成后检查主要判断支撑、相关与因果混淆、反向证据、来源冲突、关键假设、跨 Agent 伪收敛、反方审查响应、条件化建议和沙盘边依据。

质量失败必须产生返回路径：补充检索、降低对应质量状态、将边降级为假设、返回战略综合或交付“不确定结论”。质量门有权阻断正式报告、PDF 和正式沙盘。

## 可信度表达

系统不展示一个伪精确的总可信概率。它分别表达：

- 证据可用性。
- 命题支撑度与反对证据。
- 假设稳定性与失效影响。
- 因果关系存在可信度。
- 战略跨情景稳健性。
- 分析流程质量。

因果影响强度是单独的沙盘参数，不属于六维质量画像；高影响不等于高质量，高质量也不等于影响必然很大。

主界面使用“等级 + 原因 + 最脆弱环节”，具体维度分数和公式放在可展开详情中。`探讨` 的乘法门控用于判断报告是否达到交付标准，不用于声称结论正确概率。

系统降低无依据内容进入正式输出的风险，但不承诺消除幻觉。可追溯范围是用户可见命题、证据、假设、方法版本、工具调用摘要、状态变化、因果边和建议，不包含隐藏思维链。

## 方法论包

方法体系分三层：

1. 通用决策内核：类型分离、证据质检、反方、版本、质量门和复盘，不可关闭。
2. 决策类型方法包：市场进入、技术路线、资源投入、产品方向、融资投资等。
3. 行业适配模块：硬科技、机器人、机构采购、安全责任、供应链与量产等。

方法包是可执行、可测试、可版本化的分析契约，包含适用/排除条件、必需输入、诊断问题、分析方向、证据需求、Agent 角色、质量门、输出结构、沙盘映射、成本预算、评估案例和已知失败模式。

P0 内置 `hardtech-market-direction@1.1.0`。每次分析绑定具体方法版本，升级不能改写历史分析。

`ways/hardtech-market-direction/1.1.0` 是该版本唯一可编辑源资产，保存 manifest、诊断、质量门、Prompt、schema、eval 和来源清单；发布安装流程校验后生成不可变的 `method-packs/hardtech-market-direction/1.1.0`。运行时 Router 只读已发布 method-pack，不能直接执行 ways，也不能在两个目录分别编辑同一方法。

P0 只有该方法包能生成正式聚焦研究和完整战略分析。非匹配问题仍可日常问答和快速分析，但必须标注为非正式方法输出，不生成正式报告、正式 PDF 或正式沙盘。

投资项目批量筛选是活动后的第二方法包候选，不进入本次 72 小时范围，也不能复用首包 ID 冒充支持。

长期采用“开放贡献、审核发布”：所有用户可创建 Workspace 私有草稿；通过审核的专家或社区贡献可发布全局方法包；社区案例只能形成候选补丁，必须经过多案例验证、回归测试和版本审批。

## 决策跟踪与长期学习

产品跟踪决定，不管理项目。最终决定保存选择、成立条件、退出条件、关键假设、反对意见、领先指标、时间窗口和复盘日期。用户在日常问答中补充现实变化；系统识别候选影响并提醒是否重新分析。

长期产品中，每个完整闭环可投影为 `DecisionEpisode`：输入快照、方法版本、证据、分析、系统建议、用户决定、实际执行程度、外部事件、现实结果和复盘结论。P0 只保存构成该投影的 Case、Run、DecisionRecord 和 Review，不构建历史检索投影。

学习分四层：

1. 检索过去相似决策，不训练底层模型。
2. 形成经用户确认的个人校准画像。
3. 通过多案例复盘改进方法论版本。
4. 数据足够且授权明确后，训练路由、质检、因果提取或行业模型。

决策过程质量与结果质量分开评价。未采纳建议、执行偏差和外部冲击必须单独标记，不能把所有失败错误归因给分析。

## 长期社区贡献与积分（P1+）

Workspace 数据默认私有。复盘后系统可以提炼脱敏 `MethodInsight`，用户预览并授权后进入社区候选库。贡献到可撤回的方法论库和用于模型训练是两次独立授权。

贡献按质量阶段奖励积分：通过结构/脱敏审核、被独立案例验证、进入正式方法版本、在真实分析与复盘中持续产生价值。积分早期不可转让、不可提现、无现金价值，只用于产品服务。

长期商业模型：订阅覆盖日常问答和档案；固定用量档位覆盖聚焦研究与完整战略分析；付费外部数据源另行确认；私有部署采用许可与维护模式。P0 不实现支付或模拟积分账本，只记录模型、工具和连接器的实际用量元数据。

## 隐私与部署

完整 P0/MVP 是可部署、浏览器可访问的功能 Demo 候选，不是开放给真实客户数据的生产 SaaS；72 小时只交付其中的 Hackathon Prototype Slice，完整 MVP 使用 108/144 小时档或重新估算。活动后再完成生产加固和完全私有部署。P0 只承诺承载公开、已脱敏或专门用于演示的材料，不鼓励上传源代码、未申请专利核心细节、密钥、客户个人信息、原始合同和核心工艺参数。

P0 基础要求：Workspace 严格隔离；托管入口使用 HTTPS；数据库/对象存储采用部署平台提供的静态加密；BYOK 凭证应用层加密；默认不训练；文件与输入校验；敏感日志脱敏；连接器只读；提供管理员归档或通过应用级受审计流程清理 demo Workspace 的运维命令。面向最终用户的自助数据导出/删除、保留策略、社区贡献和训练授权流程属于生产加固阶段，不作为 72 小时 Prototype 完成条件。

模型、文件存储、检索、连接器和任务运行时必须通过适配层解耦，为未来私有化替换基础设施。

P0 首个基座默认使用 DeepSeek 官方 API 的 DeepSeek V4 Pro：`MODEL_PROVIDER=deepseek`、`MODEL_BASE_URL=https://api.deepseek.com`、`MODEL_NAME=deepseek-v4-pro`，均可由部署环境替换。Research/Critic/Synthesis/Validation 可先共用这一基座，但上下文、Prompt、产物、预算、事件和 tool trace 相互隔离；产品不得声称它们是四个独立基础模型。每次调用审计 provider、请求 model id 和 API 返回版本/模型标识，不持久化或展示隐藏推理内容。

## 页面与跨模式交互

登录后直接进入 Look V7 的问题工作区 `workspace`，以决策札记方式提供默认自由输入，判断/担忧/直觉/追问只是可选意图。Case 通过 Project Drawer 切换，无 Case 使用 `empty` view；当前任务只显示必要档案摘要，完整档案、挑战、证据和高级控件按需展开。

案例公共状态条在深度分析和沙盘中持续显示：证据、因果链、战略稳健性、质量门、档案/分析/沙盘版本。状态项可点击跳转到负责它的页面。
Look V7 的页面密度遵守“一屏一个主对象、至多一个支持对象”。Decision Spine 固定为问题 `workspace`、证据 `analysis`、判断 `report`、推演 `sandbox`、决定 `decision`；Review 是可恢复 dialog/drawer，不是第六主页面。系统挑战一次只展开一个；正式分析先选择 Quick / Focused / Full，并在 Focused / Full 启动前由人确认 Analysis Charter。

深度分析页负责“为什么得出判断”，展示任务进度、执行简报、详细报告、证据、反方、冲突和质量门。沙盘页负责“改变因素后发生什么”，默认先呈现最多三个脆弱条件和单变量压力测试，用自然语言解释建议保持、收窄、翻转、暂缓或证据不足；完整因果图、节点/边检查、分支比较和回滚仅在用户主动展开后出现。

多 Agent 与工具展示参考 Open WebUI 的 message-scoped `statusHistory`、TaskList、ToolCallDisplay、Citations 和 confirmation 交互，但用 Ludus 领域事件重新实现。用户看到 Agent 角色、目标、状态、工具摘要、产物和错误；不看到内部思维链。正式状态由 Postgres `analysis_events` 和 SSE/`Last-Event-ID` 提供。

跨模式链路：

```text
日常问答补充材料
→ 深度分析冻结快照
→ 报告关键假设定位到沙盘节点
→ 沙盘低置信边返回证据详情
→ 沙盘未知项回到日常问答或审核连接器/数据源补充
→ 用户采纳后生成候选档案更新
```

## P0 工程与安全边界

P0 的产品真实性依赖工程合同：HTTP schema 必须由 Pydantic/OpenAPI 单向生成 TypeScript client；Cookie mutation 必须通过 CSRF；远程内容必须通过 SSRF-safe client；高成本任务有用户/Workspace 配额；QA 不跨 owner 修改源码。多智能体容量采用 3/4/6 档，功能范围和时间承诺不能混为一谈。

## P0 完成线

72 小时评估以 Gate 0 环境通过、至少 6 个开发并发槽位、六条独立 worktree 泳道、Contract/Integration Lead 唯一合同合并权、每 6 小时集成，以及用户及时完成产品取舍与验收为前提。单 Agent、Docker/Python 3.12/DeepSeek 环境未准备或 canonical contract 未冻结时，该估算不成立。`ways` 提供首个方法源资产，Hermes 提供运行时模式，Open WebUI 提供 Web 交互模式，因此工作量按校验、安装、适配和领域重组计算，而不是按从零搭建计算。

唯一完成线是球形机器人案例的端到端链路：

```text
日常问答
→ 案例列表/创建与最小文件输入
→ 确认档案更新
→ 查看 ArgumentTree
→ 确认分析任务书
→ 信息质检与完整战略分析
→ 读取 Porter / Pre-Mortem / Counterparty / Scenario / Meadows 五项独立 artifact
→ 条件化建议和反方
→ 导出同源 HTML/PDF
→ 确认并编辑因果沙盘
→ 创建实验分支、干预变量并看到推荐翻转
→ 比较版本并可非破坏性回滚
→ 保存决定、退出条件、领先指标和复盘日期
→ 保存并读取 Review
```

Run 进行中必须可取消，取消后保留审计和已持久化阶段产物但不发布正式报告。自动复盘提醒、投资项目批量筛选和其他方法包属于活动后能力。

P0 最小文件入口明确支持 PDF/TXT/Markdown，内容先进入 Workspace-scoped RawArtifact 和信息质量流程；扩展 DOCX/CSV/JSON 属于有余量时的宽度，不影响核心完成线。

P0 不做真实支付、模拟积分账本、社区市场、方法编辑器、DecisionEpisode 历史检索投影、自动训练、跨租户学习、完全私有部署、任意自定义 MCP 端点、SSO、复杂权限、多人实时协作、项目管理、自动外部监控、精确预测和全行业方法库。审核目录中的 Exa、Firecrawl、Tavily BYOK 连接器属于 P0。

## 三个参考项目的采用边界

### Hermes Agent

许可为 MIT。采用 `tools/registry.py` 的单一注册表、`delegate_tool.py` 的隔离/权限交集/预算/tool trace、`mcp_tool.py` 的连接与 schema 模式、`skill_utils.py` 的 Skill 发现，以及迭代预算、上下文压缩和中断思想；重写为 async、Workspace-scoped Worker，不直接嵌入 `run_agent.py` 单体主循环，不继承 CLI、消息网关和通用工具全集。

### Open WebUI 0.10.2

采用认证、聊天流、文件上传、message-scoped 事件、`statusHistory`、TaskList、ToolCallDisplay、Citations、确认输入、连接器设置和进度反馈的产品模式。因其品牌许可、庞大依赖和通用聊天定位，不 fork、不复制品牌受限界面、不作为产品基座。

### 探讨

采用 `framework-selector`、商业诊断、RAG Pool、TDD 数据纳入、分析 Agent、事实调和、安全锚、战略综合、魔鬼审查、质量门、交付模板、预测日志和 lessons 复盘闭环。将文件型流程转换为数据库对象、方法包清单、AnalysisRun 状态和可测试 schema，不在生产运行时依赖临时 Markdown 文件作为唯一状态。

## Human / Analysis / Unknown 责任交互合同

朱砂红的人类承诺、深靛青的系统分析和灰赭的已知未知不是装饰性色彩，而是三类代码责任：

- Human 区只承载问题确认、偏好、范围、override、审阅、签署和接受风险；
- Analysis 区只展示 Source/Claim/Evidence/Judgment、反方、模拟与 Draft Recommendation；
- Unknown 区必须持续展示未解决问题、假设、冲突、证伪条件与建议翻转触发器。

UI 可以把三类内容并列或渐进披露，但不能让 Analysis 视觉上伪装成已签署的人类决定。Decision 主工作区必须先显示 Judgment Set、Dissent Record、条件和 Unknown，再允许人类创建 SignoffRequest；真正进入 Decided 需要独立签署动作和明确责任声明。
