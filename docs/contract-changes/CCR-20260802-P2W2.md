# CCR-20260802-P2W2 — Grey-goo wave-2: complexity downgrade, retrieval coverage, TDD discard persistence

- Status: proposed (implementation pending on `codex/lens-behavior-closed-loop`)
- Date: 2026-08-02 (Asia/Shanghai)
- Owner: backend/runtime lane (P2 wave 2)
- Affected surface:
  - `AnalysisRun` schema (`complexity_downgrade` fields) — internal state, no wire DTO change
  - New `retrieval_coverage` table + `evidence_funnel_audits` table — new read projections
  - `GET /api/workspaces/{workspaceId}/analyses/{analysisRunId}/evidence` response gains
    `funnelAudit` (discards/warnings) — additive wire field
  - SSE event `analysis.stage.progressed` payload gains optional `downgrade` marker — additive

## Problem

Grey-goo methodology v5.1 (探讨/Gray系统架构白皮书.md 第 15 章) defines three
wave-2 mechanisms that Ludus lacks:

1. **原则⑮ 复杂度自适应**: analysis depth should match the problem's real
   complexity; a depth-mode run that converges early should be able to downgrade
   mid-run instead of wasting budget. Ludus today locks `full` until the end.
2. **§3 检索纪律 / _search_index.json**: Gray centralizes retrieval, freezes a
   coverage index, and caps per-agent searches (≤3 standard / ≤5 deep) to stop
   redundant searching (Gray's real incident: ~90 searches, 1500s timeouts).
   Ludus has `_MAX_QUERIES=5` but no coverage index and no per-role quota.
3. **原则⑩ TDD 丢弃记录**: the evidence funnel already computes discards
   (factor/reason/check) but keeps them in worker memory only; the E page can
   show survivors but never "what was filtered out and why".

## Change

### 1. Complexity downgrade (AnalysisRun internal fields)

| Field | Type | Semantics |
|---|---|---|
| `complexity_downgraded` | bool (default false) | one downgrade happened this run |
| `downgrade_chain` | jsonb (default `[]`) | e.g. `["full->focused"]` with reason |

No wire DTO change: the downgrade affects BUDGET and ITERATION depth only, never
the five-lens artifact set (AGENTS section 6 contract stays intact). The
`analysis.stage.progressed` SSE payload may carry `downgrade: {from, to, reason}`
(additive, optional).

### 2. retrieval_coverage table

```sql
retrieval_coverage (
  id uuid pk,
  workspace_id uuid not null,
  analysis_run_id uuid not null,
  keywords jsonb not null,          -- normalized query keys
  queried_at timestamptz not null,
  result_summary text not null,     -- what the search found (≤500 chars)
  result_hash text not null,        -- sha256 over normalized results
  frozen boolean not null default false,
  origin_mode ... ,
  created_at timestamptz not null
)
```

Semantics: the worker's `_retrieve_once` writes one row per distinct query;
a repeat query inside the same run reuses the frozen row (idempotent) instead
of re-hitting the provider. Per-role quota: focused ≤3, full ≤5 (hard cap;
exceeding caps the packet's confidence).

### 3. evidence_funnel_audits table

```sql
evidence_funnel_audits (
  id uuid pk,
  workspace_id uuid not null,
  decision_case_id uuid not null,
  analysis_run_id uuid not null,
  stage text not null,
  admitted int not null,
  discarded jsonb not null,        -- [{factor, reason, check}]
  warnings jsonb not null,         -- [str]
  tier_counts jsonb not null,
  opposing_count int not null,
  low_tier_share numeric,
  created_at timestamptz not null
)
```

`GET .../analyses/{analysisRunId}/evidence` response gains additive
`funnelAudit` (one per run, latest stage), rendered by the E page's
"被过滤的事实" section.
